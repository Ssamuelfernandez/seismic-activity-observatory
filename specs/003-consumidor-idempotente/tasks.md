## Formato y criterios comunes

Cada tarea: `- [ ] T### [P?] [US?] Descripción con ruta`, seguida de **Cubre** (IDs) y **Criterio** (comando y resultado esperado). `[P]` = se puede hacer en paralelo con otras tareas `[P]` del mismo bloque (archivos distintos, sin dependencia pendiente); las ediciones de `CODEMAP.md` se hacen siempre en serie. Las etiquetas `[US1]…[US6]` son las historias de la spec (US1 FAQ 12, US2 reinicio y fallos, US3 cuarentena, US4 nulos y tiempos, US5 sintéticos y contadores, US6 base lista y lógica reutilizable). Las tareas de infraestructura y de cierre no llevan etiqueta.

Tres criterios comunes que **toda tarea de código** debe cumplir además de su criterio propio (no se repiten en cada tarea; el texto "CC" los invoca):

- **CC-DOC**: identificadores en inglés; docstrings y comentarios en español con la plantilla de `docs/planificacion/03-procedimiento-ejecucion.md` §7.4 (`Qué hace` / `Recibe` / `Devuelve` / `Por qué existe`, con el ID de checklist o FR cuando aplique); type hints en toda función pública; sin `print` en `common/` ni `consumer/` (solo logging), con **una excepción heredada de `002`**: los dos `print(..., file=sys.stderr)` de `common/health.py` (líneas 86 y 90), que son la salida de su CLI (`python -m common.health`); esta feature no los toca (el listado de excepciones heredadas se difiere con T089); `print` solo se permite además en los scripts CLI de `scripts/` y en `tests/support/` (salida pensada para el usuario o para la evidencia); sin `except Exception: pass`, excepciones con nombre.
- **CC-14** (constitución §14, procedimiento §7.3): una función = una responsabilidad; cuerpo ≤ ~30 líneas (el docstring de la plantilla puede superarlas, como ya se hizo en `002`, con un comentario que lo diga); archivo ≤ 250 líneas (si se supera, dividir o justificar y anotarlo en `CODEMAP.md`); hasta 4 parámetros (si no, dataclass); sin números ni textos mágicos (constantes con nombre); lo puro no importa `asyncpg` ni `aiokafka`; el SQL vive en `consumer/queries.py`.
- **CC-MAP** (CLAUDE.md): la tarea que crea, mueve o elimina un archivo de código añade o corrige en el mismo paso su fila en `CODEMAP.md` («Dónde está cada cosa»; las filas «previstas» pasan a reales). Las **evidencias** de cada bloque (salida de pytest y, si procede, SQL o logs) se guardan en `docs/evidencias/consumidor-idempotente/` en la tarea de cierre del bloque (T012, T031, T044, T061, T070, T081), que es donde se ejecutan los tests del bloque completo. Excepción: las consultas y resultados de los tests de integración de T037, T039, T040 y T042 los escribe el propio test con `tests/support/evidence.py` (T036) y T044 los recoge y verifica. (Aplicar CLAUDE.md por bloque y no por tarea es una desviación que debe confirmar el alumno: ver «Escalados», decisión (6).)

**Imagen `tests` al día (aplica a todo criterio con pytest de integración)**: la etapa `test` copia `common/` y `consumer/` dentro de la imagen, así que tras **cualquier cambio en `common/` o `consumer/`** hay que reconstruirla (`docker compose --profile test build tests`) antes de ejecutar `pytest -m integration`; si no, la prueba corre contra código viejo. Las pruebas unitarias del equipo (`uv run pytest -m "not integration"`) no lo necesitan. Los criterios de las tareas de integración no repiten este paso: se da por incluido.

Orden dentro de un bloque: la tarea de **prueba va antes que su implementación** (TDD). Una tarea de prueba "falla antes y pasa después" significa: al escribirla, `uv run pytest <archivo> -q` falla por falta de implementación (o por import); tras la tarea de implementación indicada pasa.

Comandos de referencia:

- Unitarias (equipo del alumno, sin Kafka ni PostgreSQL): `uv run pytest -m "not integration" -q`.
- Integración (dentro de la red de Compose): `docker compose up -d postgres`, `docker compose --profile test build tests`, `docker compose --profile test run --rm tests pytest -m integration -q`.
- Imagen al día antes de cualquier escenario o regresión: `docker compose build producer` (plan §8).
- Los criterios que usan `grep`, `wc`, `awk`, `ls`, `touch`, `tee` o `cut` se ejecutan en **Git Bash** (equipo Windows del alumno) o con el equivalente de PowerShell (`Select-String`, `(Get-Content f).Count`, `Get-ChildItem`, `New-Item`, `Tee-Object`). Los comandos de Docker y `uv` son iguales en ambos.
- Todo comando `python scripts/verify_consumer.py <escenario>` que use `down -v` se ejecuta con `--yes` (T073); aquí se escribe con ella.
